# 设计原则

这个文档用于功能、交互、UI 和用户工作流设计。它是一个实用的评审视角，不是要求每个小改动机械完成十项打勾。

## 默认架构：尽量解耦

- 每个模块只负责一个清楚的职责。
- 依赖稳定接口、数据契约和事件，不依赖其他模块的私有状态。
- 项目共同事实放在 `AGENTS.md`、`docs/`、任务卡和测试里；工具适配层保持薄，只做路由。
- 优先显式输入输出，避免隐藏的全局行为。
- 新增共享抽象前，先证明它至少服务多个稳定调用方；否则保持局部依赖，避免过度设计。
- 边界变化时，同时更新契约和验证方式。

## 尼尔森十大可用性原则

对 UI 或用户可见的工作流，只检查本次真正相关的原则；有意义的改动，把证据写进任务收尾或测试说明。

| 原则 | 实用检查 |
| --- | --- |
| 系统状态可见 | 用户是否能在恰当时机看到进度、成功、加载和失败？ |
| 系统与真实世界匹配 | 文案、顺序和心智模型是否贴近用户领域，而不是实现细节？ |
| 用户控制与自由 | 用户能否取消、撤销、返回，或安全退出误操作？ |
| 一致性与标准 | 标签、控件、行为和平台惯例在各处是否含义一致？ |
| 错误预防 | 能否通过约束、默认值、确认或校验，在发生前避免可预测错误？ |
| 识别而非回忆 | 选项、当前状态和下一步是否可见，而不是要求用户记住？ |
| 使用的灵活性与效率 | 高频操作是否足够快，同时不让首次使用变得难懂？ |
| 美观且极简的设计 | 页面是否聚焦任务，去掉了不必要的控件和文案？ |
| 帮助识别、诊断和恢复错误 | 错误是否用白话说明发生了什么、为什么重要、下一步怎么安全处理？ |
| 帮助与文档 | 必要帮助是否简短、可搜索、贴近场景并能直接行动？ |

## 怎么使用

1. 有意义的 UI 或行为改动前，先说清用户目标、主路径和失败/恢复路径。
2. 只选择相关原则。例如危险操作重点看错误预防和用户控制；看板重点看状态可见和识别而非回忆。
3. 用最小有效证据验证：测试、原型、截图、交互录屏、无障碍检查或手工场景。
4. 结果保持解耦：UI 应消费稳定契约，不复制业务规则，也不绑定某个 AI 工具的特殊行为。

流程复杂时，用简洁的 Mermaid 图说明；需要比较视觉方案时，用原型、截图、HTML mockup 或录屏提供比文字更可靠的证据。
